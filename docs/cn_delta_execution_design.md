# 按仓位 delta 和主力价差选择执行合约

日期：2026-11-17。状态：设计方案，尚未实现。本文的新增参数不能直接交给当前 `cn-backtest`；当前解析器会拒绝未知字段。

## 1. 用户确定的用途

用户提供品种级分钟目标仓位。目标产生买卖 delta 后，执行算法可以根据候选合约与主力之间的价差，选择合约、数量和挂单价位。主力提供比较基准，实际新增持仓可以分布在主力、次主力、远月或近月合约上。

目标变化驱动调仓。行情更新可以改变尚未完成 delta 的执行位置；已经完成的目标不因价差波动另起一次搬仓。既有到期/强制换月需求作为明确的独立事件处理，单列交易量和成本。

默认沿用品种目标名义金额：`原始权重 × 500 万元本金`，不归一化。选约算法不能改变用户的品种方向、目标金额或本金。

## 2. 先分清这笔 delta 能做什么

| 需求 | 可选择的合约 | 相对价差倾向 |
| --- | --- | --- |
| 增加多仓 | 允许开仓的候选合约 | 买入相对便宜的月份 |
| 减少多仓 | 实际持有多仓的合约，按可平数量 | 卖出相对贵的月份，同时比较平今/平昨费用 |
| 增加空仓 | 允许开仓的候选合约 | 卖出相对贵的月份 |
| 减少空仓 | 实际持有空仓的合约，按可平数量 | 买回相对便宜的月份，同时比较平仓费用 |

例如已有 5 手主力多仓，目标减少 2 手：只能从已有多仓中平 2 手。不能在没有多仓的另一个月份开 2 手空仓来代替，这会增加跨期持仓。方向反转时先完成平仓及回报确认，再分配反方向开仓。

增加多仓时选中次主力，只发生买入次主力这一腿，不凭空增加“卖主力”一腿。主力在这里是执行价格的对照。

## 3. 两张矩阵

### 合约价差矩阵：判断哪个月份合适

候选由公开 `GetContractSelections` API 返回，按实际合约代码去重。默认可选主力、OI 次主力、远月 OI 次主力、近月 OI 次主力及成交量第二名；已有持仓和未完成委托对应合约始终保留，以便平仓和处理回报。

同品种、同计量单位的两个合约 i、j：

```text
当前价差 S[i,j](t) = mid[j](t) - mid[i](t)
历史基准 H[i,j](t) = 此前有效样本中 S[i,j] 的滚动中位数
相对偏离 R[i,j](t) = S[i,j](t) - H[i,j](t)
```

每个单元格维护当前价差、历史中位数、P10/P20/P50/P80/P90、稳健波动尺度、当前分位、有效样本数、两腿可见时间和新鲜度。`R > 0` 表示 j 相对 i 比过去更贵，`R < 0` 表示更便宜。

对角线 `S[i,i] = H[i,i] = R[i,i] = 0`，不需要统计预热。反方向价差取负，分位数同时反转：`Q_p[j,i] = -Q_(1-p)[i,j]`。

执行默认取“当日主力 → 候选合约”这一行。原始跨月价差不能直接当作便宜程度；不同月份的正常升贴水可以长期不同。这里的历史基准只是执行比较模型，不保证价差会回归。

时间及统计约束：

- 只使用执行层已经收到的行情，遵守配置的行情延迟。统计、路由与挂单都不能读取撮合侧尚未投递的盘口。
- 在虚拟时间的固定 1 秒网格采样，避免成交活跃月份因更新频率高而获得更高权重。只在两腿报价均有效、未过期、时间差合格时加入样本；不跨缺口前填。
- 第一版使用最近 1,800 秒自然时间内的有效样本，至少 300 个。用于本次决定的统计只取本次决定之前的样本。午休后不足样本时重新预热，不压缩报单和回报的虚拟时间。
- 每个合约对使用有界环形窗口和有界分位统计；不载入整段历史。5 个实际候选只需维护 10 个无向合约对；保留的旧持仓和在途合约会增加数量，启动前按完整集合计算内存预算并校验显式上限。退出候选且已无持仓或委托的合约可以淘汰。
- 矩阵键是实际合约代码，不是“主力/次主力”别名。主力切换后，切换到相应实际合约对的历史；缺少该合约对样本时重新预热，不能继承别的月份的统计。
- 不同合约对的历史中位数一般不具备可加性；不能把三组价差偏离拼成“无风险套利”。

统计未预热时，可明确选择“按基准执行”或“等待”。开仓的基准是符合交易条件的主力；平仓的基准始终从实际可平仓位中选择，先比较费用，再按合约代码固定排序，不使用尚未预热的价差判断。缺少合约、缺少费率和缺少统计是不同状态，分别报告。

### 挂单价位矩阵：判断挂在哪一档

行是可执行合约，列是报价偏移。例如买单考察 `买一、买一−1 tick、买一−2 tick`，卖单考察 `卖一、卖一+1 tick、卖一+2 tick`。

每个格子展示：限价、相对主力的预计价格改善、对应开平费用、数量上限、盘口新鲜度、报单时是否意图挂单，以及与盘口的距离。第一版不编造等待时长或精确成交概率。

第一版采用可核对的选择方法：在满足最低净改善要求的格子里，优先选择最靠近盘口的价位，再按改善、有效深度和稳定顺序选合约。不能单纯最小化挂单价格成本，否则算法总会选择离盘口很远、难以成交的位置。

后续如增加成交概率模型，训练标签只能使用已经完整走完观察窗口的历史挂单；预测概率须另做校准，不能把当前 maker 的“严格击穿即全成”假设当成真实排队成交率。

## 4. 方向统一的成本比较

以主力 M 为基准，对候选 i：

```text
比较价格 F[i] = 已可见的主力中间价 + H[M,i]
买卖符号 s  = 买入 +1，卖出 −1
每手比较成本 = s × (候选限价 − F[i]) × 合约乘数
             + 本次开平类型的每手手续费
             + 显式配置的统计不确定性惩罚
```

成本越低越有利。候选相对于主力的改善为 `主力同方向比较成本 − 候选比较成本`，要求超过最小改善门槛才改变执行位置。

主力基准订单必须确实可执行，才能用于上述门槛。平仓时若没有主力持仓，主力仍提供中间价参照，但不能编造主力平仓订单或平今费率；改用实际可平集合中的基准订单作为改善门槛的对照。已有活动委托时，换单额外要求优于该委托按当前行情重新计算的成本。主力报价失效时暂停价差排名，按明确的基准/等待策略处理。

限价本身已经包含相对 mid 的买卖价差，不能再重复加一遍同口径半价差。费用按具体合约、开平类型及今昨仓计算；混合今昨仓的委托按真实可平桶拆分边际成本，遵守账户实际平仓顺序。未知费用不按零费用排名，除非用户明确选择零费用假设。

这些数值是路由用的比较指标，不直接计入账户盈亏。实际费用、成交盈亏和期末估值仍由账户模块计算；不同月份原始价差不作为额外现金损失重复扣除。

比较窗口只覆盖同品种、相同合约计量单位；不把跨品种价差混入。乘数或规格不兼容时，该组合不可选。

## 5. 建议提供的算法预设

| 预设 | 合约和时机 | 挂单方式 | 用途 |
| --- | --- | --- | --- |
| `main_baseline` | 开仓固定主力；平仓处理实际持仓，按费用和稳定顺序执行 | 当前 maker 或 IOC | 对照基准 |
| `delta_basis_best` | 在允许的开/平仓集合中，选择净比较成本最低且改善达标的合约 | 贴本合约买一/卖一 | 第一版推荐，逻辑直接 |
| `delta_basis_quantile` | 买入偏好低分位，卖出偏好高分位，再用费用和改善门槛过滤 | 贴盘口或小幅向外 | 更愿意等待价差位置 |
| `delta_basis_grid` | 以同样的主力基准比较多个合约和有限报价偏移 | 选满足改善要求且最靠近盘口的格子 | 研究合约选择与挂单距离的组合 |

可以先比较买入 P20 / 卖出 P80、最低改善 1/2/3 tick、统计窗口 10/30/60 分钟。这些是实验网格，不是已验证的最优值。

完成策略独立配置，所有预设都能使用：

- `maker_only`：到截止时间撤单，剩余需求明确保留。
- `maker_then_ioc`：到明确的等待期限后，对仍允许开/平仓的合约发保护价 IOC。平仓时仍只能从实际持仓中选择；没有完成时继续报告缺口。
- 可以增加分阶段收紧报价偏移、降低改善门槛的进度规则，时间来自固定执行窗口。不能为了挑到好价，忽略未完成量或绕过价格保护。

## 6. 示例

下表价格仅用于说明，单位为报价单位，暂不计手续费差异：

| 合约 | 身份 | 买一 / 卖一 | 当前相对主力 mid 价差 | 历史基准价差 | 相对偏离 |
| --- | --- | --- | --- | --- | --- |
| rb2701 | 主力 | 3500 / 3501 | 0 | 0 | 0 |
| rb2705 | 远月候选 | 3518 / 3519 | +18 | +25 | −7 |
| rb2612 | 近月候选 | 3492 / 3493 | −8 | −12 | +4 |

若本次需要新增多仓，`rb2705` 虽然绝对价格更高，但相对正常升水便宜了 7 个报价单位，可优先在 3518 挂买单。假设乘数 10，主力买一和远月买一相对各自比较价格的成本分别是 −5 元/手、−75 元/手，远月的相对改善为 70 元/手，再扣除两者手续费差异和统计惩罚。

若本次减少多仓，而且确实同时持有三个合约，则近月相对偏贵，可优先平近月；只有主力持仓时仍然只能平主力。若是增加空仓，方向偏好与新增多仓相反。

## 7. 数量、在途委托和防止反复换单

目标首先保留为品种级目标名义金额，而不是立即固定成一个合约的手数。每个目标批次保存一组因果的换算价格及其可见时间，用这些冻结价格核对该批次的持仓、在途委托和剩余需求，避免每次报价变动都重新生成手数 delta。

实际合约选择和整数手数仍会受成交模式、行情延迟及取整影响。比较不同算法时固定原始金额目标、时间和初始仓位，记录各自整数手数与取整偏差，不能继续声称它们使用完全相同的一份单合约 `target_lots`。

- 优先分解为平仓需求和开仓需求。平仓数量不能超过具体合约的可平仓位；一个批次可以在多个合约完成。
- 开仓每一笔取整都检查品种剩余名义金额和敞口容忍度。尾差不足一手时保留并报告；不能向上凑手或同时把同一份 delta 分给多个合约。
- 已成交但未收到回报、已发出但尚未确认的订单都占用剩余需求。撤单确认前不得释放它们的额度。
- 第一版每个品种最多一个活动子单，默认每笔 1 手。需要换合约时先撤单、等确认、根据最新已知仓位重新计算余量，再发新单。
- 设置最短挂单时间、跨合约切换改善门槛、每个目标批次最大撤改次数，避免价差在边界附近抖动造成反复切换。
- 候选池变化后，已有持仓仍可平仓；是否允许继续加仓由当时的开仓资格决定。因到期必须迁出的仓位由独立换月事件处理。
- 冻结换算价格仅用于目标完成核对。实际风险和盈亏继续按已知的新行情估值，并另记撮合侧真实敞口，不能用冻结价格掩盖价格变动。

## 8. 拟新增配置

以下是拟定接口，不是当前已支持的 TOML。推荐先实现 `delta_basis_best + maker_only`，再增加分位和网格预设。

```toml
[allocation]
algorithm = "delta_basis_best"
anchor = "dominant"
candidate_modes = ["dominant", "secondary_oi", "far_secondary_oi", "near_secondary_oi", "volume_second"]
quantity_basis = "target_notional"
min_improvement_ticks = 2.0
max_contracts_per_product = 3
max_open_orders_per_product = 1
min_previous_volume_ratio = 0.10

[allocation.basis]
method = "rolling_median"
lookback_seconds = 1800
sample_interval_ms = 1000
min_samples = 300
max_quote_age_ms = 1000
max_quote_skew_ms = 500
buy_quantile = 0.20
sell_quantile = 0.80
warmup_policy = "main_baseline"

[execution]
mode = "maker_touch"
offset_ticks = [0]
max_child_lots = 1
min_rest_ms = 1000
switch_improvement_ticks = 2.0
max_reprices_per_target = 10

[completion]
policy = "maker_only"
deadline_ms = 60000
```

`min_previous_volume_ratio` 比较候选与主力上一交易日成交量；只作为明确的流动性过滤。`max_contracts_per_product` 限制实际持仓的合约数，不限制平仓；已有持仓超出上限时只能减仓。主力或其他候选不可开仓时，不越过限制自动使用。

使用 `delta_basis_grid` 时，将执行模式改为 `maker_grid`，报价偏移可设为 `[0, 1, 2]`；使用 `delta_basis_quantile` 时才启用买卖分位门槛。`min_improvement_ticks` 按主力 tick 大小及同品种乘数换算成每手金额。配置中的门槛和窗口均为待验证的初始值。

所有算法仍遵守原有交易时段、价格网格、普通限价单的到达撮合、报撤单/回报延迟、目标覆盖和反向先平后开。成交模型版本单独保留。当前“严格击穿后全成”的 maker 模型需要与较小单笔量和保守数量约束场景一起比较，不能把候选数量增多产生的模拟成交改善直接解释为真实容量提升。

## 9. 落地边界和验收

当前代码按每个品种选定一个合约生成目标，`roll_control` 处理固定两腿。本设计需要增加品种级目标分配层，维护多个合约的实际/已知仓位和在途额度；不能只在现有 `selected_contracts` 字典里不断替换代码。

建议新增纯执行模块：`basis_matrix` 维护可见历史统计，`allocation` 计算开平需求和手数预算，`router` 返回订单意图。原撮合器负责成交，账户负责费用/盈亏。API 负责提供行情和参考数据，不替回测选择订单。

输入仍全部来自公开 API。回放需覆盖候选、持仓及未完成委托合约；预热只读目标生效之前的行情，预热期间不下单。当前历史帧 API 单请求最多 256 个合约，候选去重展开后先检查上限；超限明确拒绝，不能另开多条流悄悄改变合并顺序。

增加逐次决策审计：目标编号、delta 类型、可执行合约集合、主力身份、报价游标和时间、历史基准/分位/样本数、各候选费用与比较成本、最终限价/数量、未选原因和在途预算。矩阵明细仅在决策时或配置的采样点流式写入，工作台可以复看当时的主力行和挂单价位矩阵。

验收至少覆盖：绝对价高但相对便宜的候选；多/空开仓和减仓的四种方向；只有主力持仓时禁止在别的月份开反向仓代替平仓；手续费改变最优合约；今昨仓混合；目标反转；取消在途和晚到成交；候选重复/缺失/过期；主力换月后统计身份；窗口不足；目标不变时不产生额外搬仓；同输入重复运行一致。

比较固定主力、相对成本、分位和价位网格四组结果，保持金额目标、费用假设、延迟及完成策略一致。同时展示完成率、实际成交费用、主力基准执行差、后续 10/60 秒价格变化、品种敞口偏差、成交合约分布、撤改单数和未完成原因。参数先在较早日期选择，再在较晚日期验证。
